# TCP echo gate (porto-szb.75), 2026-11-12

**The gate (53 §2, M1 exit): TCP echo, 1 KiB, 100 connections, ≥ 1.5× uvloop streams: not met.**
porto is at parity with uvloop streams at best. Beads: porto-vw8.19 (decide what the gate should
be), porto-szb.148 (a wasted `recv` per round trip), porto-szb.149 (Linux, and the `kevent`
cost).

## What was measured, and how

- Program: `bench/micro/net_programs.py` (`tcp_echo`), the pyperf row, run by
  `uv run python bench/micro/run.py --pythons 3.14+gil --select '^tcp_echo/' --no-memory` from a
  clean tree at commit `e3375739e` (result files: `2026-11-12-e3375739e.{json,md}`; the commit
  recorded is the one that added the benchmark).
- One op is one 1 KiB round trip on one of 100 persistent connections. The server (porto's
  `serve_tcp` with `read_exact(1024)` + `write`; asyncio/uvloop `start_server` with
  `readexactly(1024)` + `write` + `drain`) runs in the benchmark's process. The load comes from one
  generator, `bench/micro/echo_client.py` (4 processes of uvloop `asyncio.Protocol` clients), the
  same for every server, run as a subprocess and timing itself from "all 100 connections open" to
  "last echo received". The clients are not porto's `_connect_tcp_numeric` streams or asyncio
  streams on the server's loop because that would make the number half client; no public
  `connect_tcp` exists yet (porto-szb.69) and threads in the server's process would fight it for
  the GIL.
- Machine: the reference machine (Apple M4 Pro, macOS 15.7.7, GIL 3.14.10 PGO+LTO, release
  porto wheel). **The machine was not quiet**: other agents were building on it (load average 12 to
  22 on 14 cores; `ash_cli` at 700 % CPU at the start, listed in the fingerprint of the result).
  AC power, Low Power Mode off. So the pyperf numbers are noisy (standard deviation 30-50 % of the
  mean, pyperf warns) and the *absolute* numbers are not the reference machine's at rest. The
  macOS caveat of 53 (an empty zero-timeout `kevent` costs ~12 µs) measured 44.5 µs in the probe
  under that load; a loaded echo server rarely polls an empty queue, so it matters less here than in
  the switch rows.

## Results

pyperf (60 values per row, per round trip): porto 10.6 µs, asyncio 12.6 µs, **uvloop streams
8.2 µs**, uvloop protocol (informative) 9.2 µs. porto is 0.77× uvloop streams, 1.2× asyncio.
Spread this large says: no better than parity.

Interleaved probe (`bench/micro/echo_probe.py --workers 8 --rounds 3000 --reps 7`, same session,
so the same noise on every server; median and minimum of 7, µs per round trip):

| server | median | min | round trips/s (median) |
|---|---:|---:|---:|
| porto (`serve_tcp`) | 7.74 | 6.68 | 129k |
| uvloop streams (the gate's baseline) | 7.73 | 7.09 | 129k |
| uvloop protocol (informative) | 6.21 | 5.64 | 161k |
| asyncio streams | 9.30 | 7.87 | 107k |

porto / uvloop streams: 1.00× (medians), 1.06× (minimums).

The generator is not the limit for the first two rows (it does 160k round trips/s against the
protocol server), but with 4 generator processes on a loaded machine it was close to it, which is
why the probe uses 8.

## Why: a profile of both servers under the same load

`sample <pid> 3` on the server process (`echo_probe.py --serve porto|uvloop`, 6 generator
processes, 12 000 rounds), samples by top of stack in the server's main thread (idle threads
and the thread waiting for the load generator left out):

| | porto | uvloop streams |
|---|---:|---:|
| `recvfrom` / `read` | 896 | 600 |
| `sendto` / `write` | 870 | 961 |
| `kevent` | 146 | 43 |
| everything else (Python, Rust, malloc) | ~150 | ~250 |

More than 90 % of both servers' time is in the three system calls. uvloop's Python-side cost
(~10 %) is all there is to win on a loopback ping-pong with synchronous `recv` + `send`, so a
runtime with *zero* overhead is capped near 1.1× uvloop here. porto's Rust and Python side is
already as small (~7 %) as uvloop's C one; it loses on the system calls themselves:

1. A request/response server reads right after it wrote, and the peer has not answered yet, so
   porto's "attempt at once whatever readiness was reported" fast path (13 §5) always starts
   with a `recv` that returns `EAGAIN`, then waits and receives again: one wasted system call per
   round trip (porto-szb.148). The profile agrees: `recvfrom` time is 1.5× uvloop's for the same
   messages.
2. porto spends 3.4× uvloop's time in `kevent` (porto-szb.149): the lane polls with a zero
   timeout after tasks finish and blocks again, where uvloop blocks once.

Fixing both would bring porto to roughly 1.05-1.1× uvloop, not 1.5×. The gate needs a
different lever (batching system calls with io_uring on Linux, or more lanes) or a different
definition: porto-vw8.19.

## Not measured

- 3.14t and 3.11: this row was run on the gating Python only.
- A quiet machine: rerun `uv run python bench/micro/run.py --pythons 3.14+gil --select '^tcp_echo/'`
  with nothing else running; the program and the generator are committed.
