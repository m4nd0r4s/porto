# 25 — CPython Integration, Memory & FFI Rules

## 1. Build matrix
CPython 3.11, 3.12, 3.13, 3.14 (GIL) and 3.14t (free-threaded, and later t builds). There is no abi3 (ADR-024). The module declares `Py_mod_gil = Py_MOD_GIL_NOT_USED` (via PyO3's `gil_used = false`).

## 2. Thread-state rules
- **P0** A lane thread creates exactly one `PyThreadState` for its lifetime (Python lanes and blocking workers). Lane 0 is the thread that called `porto.run`: it uses the state CPython already made for that thread and only detaches and reattaches it (`PyEval_SaveThread`/`PyEval_RestoreThread`); blocking workers make theirs at thread start. It never uses `PyGILState_*` on lanes, because explicit thread states are faster and safe across sub-runtime restarts.
- **P1** `Py<T>`/`PyObject*` may be *owned* only by: (a) Python lanes, (b) blocking-pool workers while running a Python job, (c) data structures whose `Drop` routes through `defer_decref`. Rust-only lanes and the driver never drop Python references directly. Three types say which: `PyObj<T>` is a reference owned by code that always runs attached ((a), (b)), and its `Drop` `debug_assert!`s `thread_is_attached()` (free in release); `PyDeferred<T>` is a reference whose owner may be dropped on any thread ((c): a message in flight, a job's result), and its `Drop` releases it directly on the lane of the runtime it belongs to and anywhere else pushes the release onto that lane's deferred-decref queue (`Handle::defer`), which the lane drains at its next maintenance tick (every `event_interval` ticks and before it parks); a body that owns Python references and is freed with its last waker (`PyTask`) moves them out in `TaskBody::release` and queues them the same way when the freeing thread is not its lane. So a coroutine, its context and its outcome are released by the lane, never by whichever thread dropped the last waker (ST-21), and the coroutine's finalizer runs there. What a release becomes when no lane can run it: queued at the moment the runtime is dropped, it runs in the runtime's drop (attached); queued after the runtime is gone, it runs at once on the releasing thread if that is attached and otherwise goes to pyo3's pool (released by the next thread that attaches); once the interpreter finalizes it is leaked (§7). A freed `PyTask` also hands its innermost scope reference to the lane: a scope node keeps the exceptions its children raised, and it keeps its ancestors (and so the scope the task was spawned into) alive, so the last reference to them is dropped on the lane in the usual case. What this does not cover: state that several owners share and none of them is the lane is released by whichever drops last (the Python `Scope` object of a scope nothing else holds, for one).
- **P2** Lanes MUST detach (`PyEval_SaveThread`) before: parking, `epoll_wait`/`turn` with nonzero timeout, futex waits, and joining threads.
- **P3** Lanes MUST NOT hold any Rust mutex while calling into Python, because Python code may re-enter Porto and deadlock. Exception: per-object critical sections managed by CPython. The rule covers every call that can run Python code, including a `Py` drop that frees the last reference (its finalizer runs) and a waker drop that frees a task. Copy what is needed out of the lock, drop the guard, then call. CI runs `scripts/check_lock_across_python.py`: a lint for the lock guards bound with `let` (`lock()`, `lock_state()`, `read()`, `write()`, `try_lock()`) that are alive at a `call*`, `getattr`/`setattr`, `get_item`/`set_item`, `Python::attach` or a running `ffi::` call, which `// lock-across-python: <why>` on the binding line waives. It is a lint and not a proof: temporaries, guards held by a callee and a drop of the last reference under a guard are for review.

## 3. Free-threaded specifics
- Use the `*Ref` C APIs (`PyDict_GetItemRef`, `PyList_GetItemRef`, `PyWeakref_GetRef`) everywhere. Lint with a CI grep that bans borrowed-ref APIs in `porto-py`.
- Python objects implemented in Rust (pyclasses) are `#[pyclass(frozen)]` wherever possible. Mutable state uses Rust atomics or `Mutex` internally, never `&mut self` pymethods on shared objects (PyO3 borrow checking under free-threading is a runtime cost and a panic source).
- Iteration over user dicts (e.g., kwargs analysis in Douro at startup) uses `Py_BEGIN_CRITICAL_SECTION` equivalents (`pyo3::sync::with_critical_section`).

## 4. Reference counting & hot paths
- Interned strings for attribute names (`"throw"`, `"_asyncio_future_blocking"`, `"send"`) are created once per interpreter (`GILOnceCell`/`PyOnceLock`).
- Results passed into `PyIter_Send` transfer ownership (steal semantics wrapper). Avoid temporary `Py_INCREF/DECREF` pairs.
- Freelists: `_Trap` (512), `_Ready` (1024), `asyncio Handle` facade objects (256).
- A freelisted object the collector can see through (one with a `__traverse__`) is tracked again only after its new value is written: `tp_alloc` returns it untracked, and the code that writes the value tracks it. Tracking it in `tp_alloc` would expose the old value, whose references were already released, to a traversal (a debug CPython traverses at once to validate).

## 6. Fork handling
`os.register_at_fork(before=…, after_in_child=…)`, registered once per process by the `fork_hooks` start step (26 §2; `os.register_at_fork` cannot be undone, so later runs find them installed):
- `before`: if a runtime is running, emit `RuntimeWarning("fork() while porto runtime is running is unsafe: …")` (the message says what to do instead).
- `after_in_child`:
  - marks every runtime that was **running** at the fork as poisoned: any use (`block_on`, `root_scope`, `shutdown`, `porto.lifecycle.shutdown_requested()`) raises `RuntimeClosed("runtime does not survive fork()…")`, and its `repr` says `poisoned by fork()`. A `Runtime` that never started holds nothing from the parent and stays usable (a deliberate narrowing of "every runtime"; a stopped one raises `RuntimeClosed` anyway).
  - clears the process-wide one-runtime flag (I1), which a child forked from another thread while a runtime ran would otherwise inherit with no thread to clear it: fresh runtimes may be created in the child.
  - if the forking thread was a lane (the fork was called from a task), it stops being one: the parent's lane context on its stack is dead, and a fresh `porto.run` may start on that thread. Such a child should end with `os._exit()` (or start a fresh runtime and then exit): returning into the parent's frames would run the parent's runtime teardown over descriptors shared with the parent.
  - clears the stale thread-locals of the forking lane thread: `porto.runtime()` there raises `NoRuntimeError`, like `in_runtime()` is false; the poisoned `Runtime` object a program kept still raises `RuntimeClosed`.
  - lets go of the signals the parent's runtime received (the signal table's lock is held across the fork by the `before` hook and released by the parent and child hooks, so a fork racing a subscription cannot leave it locked in the child): each gets its previous disposition back and nothing is written to the parent's self-pipe (18 §3), so a signal in the child never reaches the parent's runtime. The inherited hub is leaked, not dropped, because dropping it would deregister from the parent's poller.
- Windows has no `fork()`: the hooks are not registered there.

## 7. Interpreter finalization
At `Py_Finalize`, an `atexit` hook shuts down any runtime still running. Lanes must not touch Python after `Py_IsFinalizing()` is true. They drop deferred decrefs without executing them (leak instead of crash).

## 8. Panics
- `porto-py` is built with `panic = "unwind"`: the release, `dist` and dev profiles say so, and `porto-core` and `porto-py` refuse to compile under `panic = "abort"` (`#[cfg(panic = "abort")] compile_error!`).
- Every FFI entry point catches unwinds. `#[pyfunction]`/`#[pymethods]` bodies are wrapped by pyo3, which turns a panic into `pyo3_runtime.PanicException` (a `BaseException`) raised in the caller; the raw slots (`am_send`, `tp_iternext`, the raw methods) and the ABI functions catch it themselves and raise `RustPanic`. No panic ever unwinds into CPython.
- **Inside a task poll** (the step loop, a Rust future the task awaits, a driver bug) → the step loop catches it and raises `porto.RustPanic` (`message`, `location` = `file:line:column`, recorded by a panic hook chained at module init, which still logs to stderr) *in the coroutine*, at the `await` it was suspended in, as if that await had failed (the Rust future that panicked is dropped). The task then unwinds like for any exception, in its own `contextvars` context and as the running task: scopes it entered cancel their children and wait for them, `finally` blocks run (and may `shield` cleanup), and the `RustPanic` reaches the scope the task was spawned into (C4) only after that subtree drained; joiners get it; the lane keeps running other tasks. Two cases do not drain the subtree, and the children of the task's open scopes are then only cancelled when their coroutines are freed (after the run, where a `shield` in their cleanup fails): a panic in the scope-exit wait itself (the exit is abandoned to throw the `RustPanic` at it), and a second panic during that unwind, which closes the coroutine at once (in its context, where a scope exit cannot wait) and fails the task with the first `RustPanic`. A panic the coroutine catches, followed by a yield, makes the next panic a first one again; a panic outside the stepping (the poll's own bookkeeping) fails the task with a `RustPanic` through `PyTask::poll`, without running the coroutine's cleanup. A `PanicException` that a coroutine does not handle and lets escape is replaced by `RustPanic` the same way (the original is its `__cause__`); one the coroutine catches stays an ordinary `BaseException`. The location slot is per thread: a `PanicException` raised in a `to_thread` job may carry no location when it becomes a `RustPanic` on the lane.
- **Inside scheduler internals** (queues, timers, driver, the lane's own futures: any unwind that reaches the lane's `block_on`) → one line to stderr, then `std::process::abort()`. A broken scheduler cannot be repaired by failing a task.
