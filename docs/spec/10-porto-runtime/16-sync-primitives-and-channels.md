# 16 — Synchronization Primitives & Channels

All primitives are implemented in Rust (`porto-core::sync`) and are **thread-safe**. They may be shared across lanes and used from Rust tasks. From non-runtime threads, they are used via `blocking_*` methods, which are never allowed on lane threads (they raise `RuntimeError`). A `blocking_*` wait runs with the thread detached from Python and does not check for signals: Ctrl-C does not interrupt it (the `KeyboardInterrupt` is raised once the wait is over).

Waiting tasks use intrusive `WaitNode`s embedded in the task (PyTask: `wait_node`; RustTask: inside the future). Queues are FIFO (fair) unless stated otherwise.

## 1. Primitives

| Python | Rust | Semantics |
|---|---|---|
| `porto.Lock()` | `sync::Mutex<()>` | async, fair FIFO handoff, non-reentrant; `async with lock:`; `await acquire()`, `release()`; `locked()`; `try_acquire() -> bool`; `blocking_acquire()`. The holder is not recorded (as in `asyncio.Lock`): a `release()` by a task that does not hold the lock, or a second `release()`, releases it from under the holder and breaks mutual exclusion; only a release of an unlocked lock raises `RuntimeError` |
| `porto.Mutex[T](value)` | `porto.Lock` + the value | lock that owns the value: `async with m as v:` gives a `MutexGuard[T]`: `v.value`, `v.set(new)`, unusable once the block exits; `locked()`; encourages correct free-threaded code |
| `porto.RwLock()` | `sync::RwLock` | writer-preferring: a reader never takes the lock while a writer waits (it queues behind it); waiters are otherwise served in arrival order, consecutive readers together, so neither readers nor writers starve. `async with lock.read():`, `async with lock.write():` (the entry `read()`/`write()` returns is its own context manager, lazy like `Lock`'s); `acquire_read()`/`release_read()`, `acquire_write()`/`release_write()`, `try_acquire_read()`/`try_acquire_write()`, `readers`, `write_locked()`, `blocking_acquire_read()`/`blocking_acquire_write()`. Holders are not recorded; a release while no reader (writer) holds it raises `RuntimeError` |
| `porto.Semaphore(n)` | `sync::Semaphore` | `acquire(k=1)`, `release(k=1)`, `async with` (one permit), `available`, `try_acquire(k=1)`, `blocking_acquire(k=1)`. Fair: a waiter that wants more permits than are free blocks the ones behind it. **Bounded**: `release` of more permits than are acquired raises `ValueError` (unlike `asyncio.Semaphore`; like `BoundedSemaphore`), so `n` is at least 1, and a count outside `1..=n` raises `ValueError` (it could never be granted). For signalling between tasks use `Event` or `Notify` |
| `porto.CapacityLimiter(n)` | Semaphore + owner tracking | AnyIO-compatible: `total_tokens` (an `int` ≥ 1 or `math.inf`; settable: raising it grants waiters, lowering it takes tokens back as they are released), `borrowed_tokens`, `available_tokens`, `acquire()`, `acquire_nowait()` (`porto.WouldBlock` when none is free), `acquire_on_behalf_of(b)`, `acquire_on_behalf_of_nowait(b)`, `release()`, `release_on_behalf_of(b)`, `async with`. The default borrower is the running porto task; any other borrower is compared by identity. A borrower holds at most one token: borrowing again raises `RuntimeError` (before waiting), and so does releasing a token it does not hold |
| `porto.Event()` | `sync::Event` | `set()`, `is_set()`, `await wait()`, `blocking_wait()`. Not clearable (Trio semantics); for clearable events use `watch` |
| `porto.Notify()` | `sync::Notify` | `notify_one()` (stores a permit if nobody waits), `notify_all()`, `await notified()`, `blocking_notified()` |
| `porto.Condition(lock=None)` | `sync::Condvar` + a `porto.Lock` | `wait()`, `wait_for(pred)`, `notify(n=1)`, `notify_all()`, `async with`, `acquire()`, `release()`, `locked()`, `lock`. `lock` must be a `porto.Lock` (`TypeError` otherwise). `wait()` queues the task *before* it releases the lock, so a notification sent after the release is never missed, then takes the lock again before it returns, **also when cancelled**: the `Cancelled` is raised once the lock is held again (the lock wait is a `NotifiedShielded` trap, 11 §5.2). `wait_for(pred)` checks `pred()` first and after each notification, with the lock held, and evaluates to its result. `wait`, `notify` and `notify_all` without the lock held raise `RuntimeError`. Notifications are not stored; one whose task was cancelled before it observed it goes to the next waiter. A wait closed (`GeneratorExit`) cannot wait for the lock: it takes the lock back only if it is free. If another task holds it (or was handed it), the close raises an internal `BaseException` in place of `GeneratorExit`, which the closing coroutines carry up to that lock's `async with` exit: the exit releases nothing and goes on as `GeneratorExit`, so the holder keeps the lock. Code that releases the lock by hand around `wait()` gets no such protection |
| `porto.Barrier(n)` | `sync::Barrier` | `await wait() -> bool`: True for the leader, the last arrival of a round, exactly one per round; the barrier is reusable. A task cancelled while it waits leaves its round, which then waits for one more arrival. `parties`, `n_waiting`, `blocking_wait()`; `n` ≥ 1 |

Cancellation: a cancelled waiter is removed from the queue. If a cancelled waiter had **already been granted** the lock or permit (a race between grant and cancel), it passes the grant on to the next waiter. This invariant is tested with loom.

Awaiting: `wait()`, `notified()`, `acquire()` (and `acquire_read()`, `acquire_write()`, `acquire_on_behalf_of()`, `wait_for()`) return lazy awaitables; nothing is taken until they are awaited, so one created and never awaited holds no lock and consumes no permit (it emits `RuntimeWarning` when freed, `11` §10). A grant is taken only in the step that resumes the coroutine with it: a wait that completes at once but finds the task's budget spent (T2) yields first and takes the grant afterwards, never the other way round. A task closed or cancelled at any suspension point therefore never holds a grant it did not observe.

`async with` on a `Lock`, `Mutex`, `Semaphore`, `CapacityLimiter`, `Condition`, `lock.read()` or `lock.write()` follows the same rule: `__aenter__()` returns a lazy entry that waits like `acquire()` and takes nothing itself (for a `Mutex`, the entry is the new `MutexGuard`, which the await evaluates to; the guard refuses `value` and `set()` until then). The statement awaits it at once, and its first resume takes a free lock without suspending (a T2 synchronous completion: it raises `Cancelled` first if the task is cancelled, and spends a unit of the budget). An exception between the call and the await (from 3.14 a profile or trace hook runs there, and a `KeyboardInterrupt` can land there) therefore leaves the lock free, and an `__aenter__()` dropped unawaited takes nothing and warns like `acquire()`. Outside a porto runtime, awaiting the entry raises `NoRuntimeError`.

The result of an await can outlive the last reference the task holds, until the task next suspends or ends. On 3.12+ GIL builds, a porto awaitable that completes with a value other than `None` can return it through one reused `StopIteration` (`11` §6), which keeps the latest such result until the task gives its lane up: after `async with mutex as guard:` and `del guard` in the same step, the guard (and the mutex it references) is freed only at the task's next suspension. Code MUST NOT rely on an await's result being freed before the task next suspends. 3.11 and free-threaded builds do not keep it.

## 2. Channels

```python
tx, rx = porto.channel[T](capacity: int)         # bounded MPMC (clone both ends)
tx, rx = porto.unbounded_channel[T]()            # explicit opt-in
tx, rx = porto.oneshot[T]()
tx, rx = porto.broadcast[T](capacity)            # each rx gets every msg; lagging → porto.Lagged(n)
tx, rx = porto.watch[T](initial)                 # latest-value; rx.changed(), rx.borrow()
```

### 2.1 Sender API
`await tx.send(v)` (waits when full), `tx.try_send(v)` (raises `porto.WouldBlock`), `tx.clone()`, `tx.close()`, `async with tx:` (closes on exit), `tx.blocking_send(v)` (non-lane threads only), `tx.capacity`, `tx.is_closed()`.

### 2.2 Receiver API
`await rx.recv()` (raises `porto.EndOfChannel` when closed and drained), `rx.try_recv()`, `async for v in rx:`, `rx.clone()`, `rx.close()`, `rx.blocking_recv()`, `await rx.recv_many(max)` → `list[T]` (batching, important for throughput).

### 2.3 Closure semantics
The channel closes when all senders are closed or dropped (receivers see the end after draining), or when all receivers are dropped (sends raise `porto.BrokenResourceError`). Dropping a handle is equivalent to closing it, and works on refcount release. Using a handle that was itself closed raises `porto.ClosedResourceError` (the program closed it) rather than `EndOfChannel` or `BrokenResourceError` (the other side went away). Full and empty `try_send`/`try_recv` raise `porto.WouldBlock`. `channel()` without a capacity is a `TypeError` that names `unbounded_channel()`.

### 2.4 Implementation notes
- Bounded MPMC: a Vyukov array-based queue (the `crossbeam::ArrayQueue` design, vendored so that loom models its atomics) plus two waiter lists (senders and receivers), each a wait queue under its own small mutex. Fast path: lock-free push/pop, then a `SeqCst` fence and a load of the other side's waiter hint; the lock is taken only when someone waits. Wake exactly one counterpart; a woken waiter retries (a waiter not yet queued may take the value or room first), and a woken waiter cancelled before retrying passes the wake on.
- Unbounded: a deque under a mutex; senders never wait, receivers wait as for the bounded channel.
- Python waits: `await tx.send(v)` / `await rx.recv()` do nothing until awaited, then try the fast path; if they must wait, the task parks its embedded `wait_node` on the waiter list (a `Notified` trap whose target is the handle, no allocation besides the trap) and retries when woken. The waiter's last look under the lock checks the buffer's length instead of pushing or popping, with the same hint-and-fence handshake, so the value never has to travel through the wake.
- Cancellation: a channel op that completes without waiting is a synchronous completion (`11` §5.3, T2), so it is a checkpoint like any other: when the task's effective scope is cancelled, the first resume of `send`, `recv`, `recv_many` or `__anext__` raises `Cancelled` before it tries anything (nothing is sent or taken, and it wins over a closed-channel error), and otherwise spends a unit of the budget. A shield (`15`) suspends this. Only the first resume checks: a retry after a wake always acts on the wake it observed, and a cancellation that arrives while the task waits is delivered by the driver (T3).
- Closing a handle (`close()`, or dropping it) is per handle. A task or thread already waiting through that handle wakes and raises `porto.ClosedResourceError`; waiters on other handles keep waiting. A send that races with the last receiver's close may succeed; its value is dropped with the channel.
- Elements are `PyObj`. Moving an object between lanes requires no copy; the free-threaded refcount handles ownership. On the GIL build, all Python tasks are on lane 0 anyway.
- Rust-side channels (`porto::sync::mpsc`) are generic over `T: Send`. The Python channel is `T = PyObj`.

### 2.5 Oneshot, watch and broadcast
The three constructors that are not queues return pairs of their own classes (`OneshotSender[T]`/`OneshotReceiver[T]`, and below `WatchSender`/`WatchReceiver`, `BroadcastSender`/`BroadcastReceiver`), because their methods differ from the queue's. What they share with `channel`: the errors (§2.3: `EndOfChannel` when the other side ended, `BrokenResourceError` when every receiver is gone, `ClosedResourceError` for a handle the program closed), `try_recv`/`blocking_recv`, `async for`, `close()` and `async with tx:`, dropping a handle closes it, and a never-awaited `recv()` warns and takes nothing. **None of them has a sender that waits, so `send` is a plain call, not awaited** (a type checker flags `await tx.send(v)`); `recv_many`, `capacity` and `try_send` are only on `channel`.

**`oneshot[T]()`** (`sync::oneshot`): one value. `tx.send(v)` uses the sender up (a second `send` raises `ClosedResourceError`); it raises `BrokenResourceError` if the receiver is closed or dropped, and the value is dropped with it. `await rx.recv()` raises `EndOfChannel` if the sender was closed or dropped without sending, and also after the value was received (`async for` yields the one value, then ends). No clone. The value sits in a slot until a receive takes it, and a wake only says "look again", so a waiter cancelled after a wake loses nothing: the next receive finds the value (loom-tested). Several tasks may await one receiver: the value goes to one, the others see the end.

**`watch[T](initial)`** (`sync::watch`): the latest value. Every `tx.send(v)` replaces it and makes the next *version* (the value starts at version 0). A receiver remembers the newest version it has seen: `await rx.changed()` completes once there is a newer one and marks it seen, so several sends before the call coalesce into one completion and the initial value is seen from the start; `rx.borrow()` returns the current value without marking anything seen, `rx.borrow_and_update()` marks it; `rx.has_changed()`, `rx.try_changed()` (`WouldBlock` when nothing is new), `rx.blocking_changed()`; `async for v in rx` yields the latest value after each change (not the initial one). `rx.clone()` has seen what the original had, and `tx.subscribe()` makes a receiver that has seen the current version. Senders and receivers clone; the channel ends for receivers when every sender is closed or dropped, after a change they had not seen (`changed()` then raises `EndOfChannel`), and `borrow()` keeps returning the last value. A `send` while no receiver is open raises `BrokenResourceError` and stores nothing; unlike `channel`, that is not permanent, since `tx.subscribe()` makes a new receiver. Several tasks may await one receiver, which gives each version to one of them; give each task its own `rx.clone()` to have every task see every version. **The clearable event** that the table in §1 points to is `watch[bool](False)`: `tx.send(True)` sets it, `tx.send(False)` clears it, and `while not rx.borrow(): await rx.changed()` waits for it (a set that was cleared again before the waiter ran is not seen, as for any level-triggered flag). Cancellation: a wake only says "look again" and the version stays unseen until a `changed()` completes, so a cancelled waiter loses nothing and every send wakes every waiter (loom-tested).

## 3. Select (choice over several events)
`porto.select(*branches)` is deliberately **not** provided in v1. Users write a scope with competing tasks plus `scope.cancel()`, or use `rx.recv_many`. Rationale: select-style cancellation of partially completed ops is the main source of lost-message bugs in Tokio. Revisit after v1 (`55`).
